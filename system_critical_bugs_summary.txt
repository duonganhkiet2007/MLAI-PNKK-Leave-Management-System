1. LOST WAKE-UP RACE CONDITION (Mức độ: CRITICAL)
- Vị trí mã nguồn:
  * backend/services/orchestration.py (dòng 1088 - 1110)
  * backend/services/inspection_service.py (dòng 504 - 514)
- Cơ chế lỗi:
  VLM Worker hoàn tất kiểm định và gọi resume_pending_requests_for_proof() ngay
  trong khoảng trống giữa lúc API đọc proof status là 'PROCESSING' và lúc ghi đơn
  vào SQLite. Tại thời điểm worker quét DB, đơn chưa kịp lưu nên worker thấy 0 đơn
  chờ. Sau đó, API mới lưu đơn vào DB với status = 'PROCESSING'.
- Hậu quả:
  Đơn bị treo vĩnh viễn ở trạng thái PROCESSING (mất tín hiệu đánh thức).
- Hướng xử lý:
  Bọc kiểm tra trạng thái chứng từ và lưu đơn trong cùng write transaction, hoặc
  worker kích hoạt completion event/callback kiểm tra lại sau khi đơn lưu xong.

2. STALE FAILURE GHI ĐÈ STATE MỚI (Mức độ: CRITICAL)
- Vị trí mã nguồn:
  * backend/services/inspection_service.py (dòng 450 - 480: _apply_inspection_failure)
- Cơ chế lỗi:
  Hàm _apply_inspection_failure hoàn toàn không kiểm tra inspection_version (khác
  với hàm _apply_inspection_success). Khi user re-upload chứng từ mới (version 2 đã
  READY), một job lỗi cũ của version 1 chạy retry thất bại sẽ thực thi câu lệnh SQL
  ghi đè vô điều kiện:
  UPDATE proof_documents SET inspection_status='FAILED', vlm_error=? WHERE id=?
- Hậu quả:
  Tác vụ cũ bị lỗi xóa sổ trạng thái READY hợp lệ của chứng từ mới tải lên.
- Hướng xử lý:
  Thêm mệnh đề so khớp version: WHERE id=? AND inspection_version=?. Nếu version
  đã thay đổi, lập tức hủy bỏ cập nhật lỗi và discard job.

4. RECOVERY AMNESIA KHI SERVER RESTART (Mức độ: HIGH)
- Vị trí mã nguồn:
  * backend/services/inspection_service.py (dòng 103 - 137: recover_interrupted_jobs)
- Cơ chế lỗi:
  Hàm phục hồi chỉ quét bảng proof_inspection_jobs đang PROCESSING để reset lại.
  Nếu job đã chạm trần retry và bị đánh dấu FAILED, hàm không hề gọi
  resume_pending_requests_for_proof(). Đồng thời, hàm hoàn toàn không quét bảng
  leave_requests để tìm những đơn bị bỏ dở trong khi proof đã hoàn thành từ trước.
- Hậu quả:
  Đơn bị treo vô thời hạn sau khi khởi động lại server.
- Hướng xử lý:
  Bổ sung bước quét các leave_requests có status IN ('PROCESSING', 'PENDING_INSPECTION')
  để tái đánh giá (re-evaluate) và kích hoạt lại sau restart.

5. LỖ HỔNG FAIL-OPEN DUYỆT ĐƠN TRÁI PHÉP (Mức độ: CRITICAL)
- Vị trí mã nguồn:
  * backend/services/orchestration.py (dòng 1193 - 1200: process_human_decision)
- Cơ chế lỗi:
  Parser phân tích text phản hồi tự do của cấp quản lý bằng từ khóa đơn giản:
  chỉ tìm từ khóa từ chối ("TỪ CHỐI", "REJECT", "BÁC BỎ") hoặc sửa đổi ("BỔ SUNG",
  "SỬA"). Mọi câu phản hồi mang tính phân vân, hoãn lại hoặc chất vấn (ví dụ:
  "Để tôi xem lại sau", "Chưa duyệt được", "Cần họp lại") rơi vào:
  else: act = 'APPROVE_OVERRIDE'
- Hậu quả:
  Hệ thống tự động DUYỆT ĐƠN ngay lập tức, vi phạm nguyên tắc an toàn Zero-Trust.
- Hướng xử lý:
  Chuyển sang cơ chế Fail-Closed: Bắt buộc có từ khóa phê duyệt rõ ràng mới gán
  APPROVE; nếu text mơ hồ hoặc không nhận diện được, giữ nguyên PENDING_ESCALATION
  hoặc yêu cầu chọn action tường minh.

6. FUZZY IDENTITY SPOOFING / LỌT CHỨNG TỪ GIẢ (Mức độ: CRITICAL)
- Vị trí mã nguồn:
  * core/domain.py (dòng 111 - 123: names_approximately_match)
- Cơ chế lỗi:
  Thuật toán trả về True nếu token cuối trùng nhau (left_tokens[-1] == right_tokens[-1])
  hoặc bất kỳ từ đơn lẻ nào có SequenceMatcher ratio >= 0.82.
- Hậu quả:
  "Nguyễn Văn An" và "Trần Thị An", hoặc "Benchmark Person 999" và "Benchmark Person 000"
  đều được coi là cùng một người. Nhân viên có thể mượn giấy nhập viện/phẫu thuật
  của người khác trùng họ hoặc trùng tên để hưởng phép ốm nguyên lương.
- Hướng xử lý:
  So khớp toàn bộ chuỗi họ và tên đã chuẩn hóa (Full Name Match), hoặc tính độ tương
  đồng trên toàn bộ xâu (Full String Similarity >= 0.88), không so sánh rời rạc
  từng token đơn lẻ.

9. ASGI EVENT LOOP STARVATION DO BLOCKING I/O (Mức độ: HIGH)
- Vị trí mã nguồn:
  * backend/routers/leave_router.py (dòng 88 - 120: upload_proof)
- Cơ chế lỗi:
  Endpoint khai báo async def upload_proof(...), nhưng bên trong lại gọi ghi đĩa
  đồng bộ (path.open('xb').write() với tệp tới 10MB) và transaction SQLite đồng bộ
  (st.transaction()).
- Hậu quả:
  Chạy blocking I/O trên Event Loop chính của FastAPI làm nghẽn toàn bộ luồng xử lý,
  khiến tất cả request đồng thời khác của hệ thống bị chậm hoặc timeout.
- Hướng xử lý:
  Chuyển thành def upload_proof đồng bộ (để FastAPI tự dispatch vào threadpool)
  hoặc bọc I/O qua anyio.to_thread.run_sync.

10. TRANH CHẤP KHÓA SQLITE WAL TRÊN Ổ MẠNG NFS (Mức độ: HIGH)
- Vị trí mã nguồn:
  * backend/database.py (dòng 25 - 36: get_db_connection)
  * Môi trường lưu trữ: /workingspace_aiclub/
- Cơ chế lỗi:
  Hệ thống chạy trên phân vùng mạng NFS nhưng thực thi PRAGMA journal_mode=WAL
  trên mỗi lần mở kết nối. SQLite WAL sử dụng bộ nhớ chia sẻ POSIX (mmap trên file
  -shm), vốn không tương thích và không coherent trên giao thức NFS. Đồng thời,
  việc unlinked open file handle tạo ra hàng loạt file ma dạng .nfs*.
- Hậu quả:
  Thường xuyên phát sinh lỗi sqlite3.OperationalError: database is locked và có rủi
  ro hỏng cơ sở dữ liệu.
- Hướng xử lý:
  Cấu hình chuyển đường dẫn DB_PATH sang thư mục đĩa cục bộ (/tmp hoặc local disk)
  hoặc chuyển sang cơ sở dữ liệu Client-Server (PostgreSQL) khi chạy đa tiến trình.
